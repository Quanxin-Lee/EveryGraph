# Graphics and runtime architecture evidence for EveryGraph

**Research date: 2026-10-30. Scope: planning, not implementation.**

These projects offer different architectural precedents: Blender separates graphics backends from dependency evaluation; GEGL evaluates image-processing graphs; napari separates scientific data models from presentation; Zed separates an application from its GPU UI framework; llama.cpp separates inference policy from device computation. Those distinctions, rather than superficial UI similarities, are the useful comparison. **[I]** EveryGraph should borrow boundaries and contracts, not assume any single project supplies its complete architecture.

## Evidence legend and reproducibility

- **[D] Official docs:** upstream documentation, license statements, or release metadata; authoritative statements of intent, not execution tests.
- **[S] Source-verified:** inspected build files, implementation, headers, or license files at the exact commit below. A source citation identifies a file and line range or symbol.
- **[I] Inference:** an architectural lesson or recommendation derived from cited evidence, not an upstream guarantee.
- **[U] Unknown:** not established by this inspection; requires further investigation or testing.

GitHub access used `gh api`: repository metadata, branch commits, tags, release records, recursive trees, and file contents fetched with `ref=<SHA>`. No upstream code was executed or built. GitHub-hosted Blender/GNOME sources were inspected as upstream mirrors; absence of GitHub release objects does not mean absence of releases.

## 1. Blender: backend abstraction and dependency evaluation

**[S] Graphics implementation.** All three backend implementations remain present. `B:source/blender/gpu/intern/gpu_context.cc::gpu_backend_create` conditionally constructs `GLBackend`, `VKBackend`, or `MTLBackend`; the GPU module’s CMake file conditionally includes their sources. Top-level CMake lines 970–995 enable OpenGL and Vulkan build options by default outside Apple platforms; Apple disables OpenGL, enables Metal, and offers Vulkan as an OFF-by-default development option. These are build defaults, not proof of the backend selected by every distributed binary or GPU. [Backend factory](https://github.com/blender/blender/blob/7a8010992fe65512be4c841f6071c9654a0fff94/source/blender/gpu/intern/gpu_context.cc#L564-L591); [build options](https://github.com/blender/blender/blob/7a8010992fe65512be4c841f6071c9654a0fff94/CMakeLists.txt#L970-L995).

**[S/D] Shader contract.** `GPUBackend` exposes resource allocation and compute dispatch through virtual methods (`B:source/blender/gpu/intern/gpu_backend.hh`, lines 43–98). `ShaderCreateInfo` describes stage sources, resource bindings, and push constants, rather than exposing one platform’s shader objects. The [official GPU documentation](https://developer.blender.org/docs/features/gpu/) identifies Blender Shading Language and preprocessing. Concrete lowering remains backend-specific: `B:source/blender/gpu/metal/mtl_shader.mm`, lines 292–320, preprocesses source and calls `newLibraryWithSource`; `B:source/blender/gpu/vulkan/vk_shader_compiler.cc::compile_ex` calls `CompileGlslToSpv`; `B:source/blender/gpu/opengl/gl_shader.cc`, lines 1277–1279, calls `glShaderSource`/`glCompileShader`. This is not evidence for one unchanged shader binary across APIs.

**[S] Dependency execution.** The depsgraph is not the GPU command graph. `B:source/blender/depsgraph/intern/eval/deg_eval_flush.cc::deg_graph_flush_updates` propagates update tags outward through relations. In `deg_eval.cc`, `schedule_node` rejects clean operations and waits for pending parents; `deg_task_run_func` evaluates an operation and queues children through `BLI_task_pool_push`. Evaluation distinguishes copy-on-eval, threaded work, and a single-threaded workaround stage. `B:source/blender/blenlib/intern/task_scheduler.cc::BLI_task_scheduler_init` integrates TBB when compiled in and controls parallelism. Consequently, “all nodes run concurrently” would misdescribe the implementation. [Scheduling conditions](https://github.com/blender/blender/blob/7a8010992fe65512be4c841f6071c9654a0fff94/source/blender/depsgraph/intern/eval/deg_eval.cc#L272-L315).

**[S] Python boundary.** `B:source/blender/python/intern/bpy_interface.cc::BPY_python_start` initializes embedded CPython through `PyConfig` and `Py_InitializeFromConfig`; surrounding context helpers acquire/release the GIL. `WITH_PYTHON_MODULE` is a distinct, normally disabled build mode for importing Blender without its UI (`B:CMakeLists.txt`, lines 209–227). Add-on activation imports Python modules and invokes `register()` in `B:scripts/modules/addon_utils.py::enable`; disabling invokes `unregister()`. **[I]** Neither CPython’s “isolated config” nor registration hooks constitute an OS sandbox. The script-autoexecution build setting is a policy control, not confinement of code once authorized.

**[S/D] Licensing.** `B:COPYING` directs users to GPLv2; inspected GPU and Python source headers specify `GPL-2.0-or-later`. The [official license page](https://www.blender.org/about/license/) confirms GPLv2-or-later and separately identifies exceptions such as Apache-licensed Cycles and Python’s own license. Do not infer that every bundled library shares the application license.

**[I] Lesson / do not copy.** Adopt declarative graphics interfaces, dirty-state propagation, and explicit scheduler exceptions. Do not transplant Blender’s entire scene database, shader toolchain, or GPL implementation merely to obtain those ideas; do not equate its graphics backend with an inference backend.

## 2. GIMP and GEGL: processing regions versus process boundaries

**[S] Composition.** GIMP’s Meson build declares C/C++ and links `gegl-0.4` (`G:meson.build`, lines 1–7, 467–468). Its drawable-filter code constructs GEGL nodes and assigns operations (`G:app/core/gimpdrawablefilter.c`, lines 793–838). GEGL’s `GeglNode` either carries an operation or contains children connected through proxies; named pads connect processing elements (`E:gegl/graph/gegl-node.h`, lines 25–87; `gegl-node.c::gegl_node_connect_to`). `GeglOperation` is a GObject-based operation with introspectable properties—not a separate process per graph node.

**[S] Demand and invalidation.** `E:gegl/operation/gegl-operation.h::GeglOperationClass` separates `get_required_for_output` from `get_invalidated_by_change`: the input area required to calculate output is a different contract from the output area dirtied by an input change. Traversal combines upstream requirements, recognizes sufficiently cached regions, then calls operations (`E:gegl/process/gegl-graph-traversal.c`, lines 316–354, 484–490). `E:gegl/graph/gegl-node.c::gegl_node_invalidated_invalidate_node` transforms and propagates invalidated regions through downstream operations. **[I]** Filters with neighborhood dependencies need these explicit spatial contracts; invalidating only the originally edited pixels would be insufficient. [Operation contract](https://github.com/GNOME/gegl/blob/c9a042936f7b8f05c691e93f7db86f20feb6b72f/gegl/operation/gegl-operation.h#L100-L129).

**[S] Two cache concerns.** `GeglCache` subclasses `GeglBuffer` and tracks valid regions by mip level; `gegl_cache_invalidate` subtracts regions and `gegl_cache_computed` adds them (`E:gegl/graph/gegl-cache.c`, lines 60–73, 259–311). Separately, tile-cache storage tracks approximate bytes and trims toward `gegl_buffer_config()->tile_cache_size` (`E:gegl/buffer/gegl-tile-handler-cache.c::gegl_tile_handler_cache_trim`). The swap backend implements compression and starts a dedicated swap-writer thread (`E:gegl/buffer/gegl-tile-backend-swap.c`, lines 290–293, 1494–1497). **[I]** Cache validity, residency, and disk spilling are distinct responsibilities; a tile-cache target is not a hard cap on total process memory.

**[S] Processing and threading.** `E:gegl/process/gegl-processor.c::gegl_processor_work` performs incremental rendering and reports whether work remains. Chunk size controls processing granularity; it is not one thread per node. `E:gegl/gegl-parallel.c` partitions ranges/areas and creates GThread workers. Operation classes expose a `threaded` opt-in/out and OpenCL support flag; OpenCL use additionally depends on runtime acceleration checks (`E:gegl/operation/gegl-operation.h`, lines 80–90; `gegl-operation.c::gegl_operation_use_opencl`). No universal parallelism or GPU-coverage guarantee follows.

**[S] Crucial isolation distinction.** GIMP’s `gimp_plug_in_open` creates bidirectional pipes and launches a child through `gimp_spawn_async`, retaining its PID for lifecycle management (`G:app/plug-in/gimpplugin.c`, lines 463–465, 569–594). GEGL instead loads operation modules with `g_module_open`, resolves `gegl_module_register`, and directly invokes `klass->process` (`E:gegl/module/geglmodule.c`; `E:gegl/operation/gegl-operation.c`, lines 166–176). [GIMP launch](https://github.com/GNOME/gimp/blob/3a7fa758c330a0179fed07fe955d07b38283b457/app/plug-in/gimpplugin.c#L569-L594).

**[I/U] Security limits.** A child process provides an address-space/lifecycle boundary, not proof of restricted filesystem, network, privileges, or resource consumption. The inspected launcher does not establish an adversarial plug-in sandbox; GEGL native operations execute inside their host. Package-specific OS restrictions were not audited. Killing a child also does not imply rollback of already requested document edits.

**[S] Licenses.** GIMP core headers specify GPLv3-or-later; `G:LICENSE` distinguishes LGPL libraries and explicitly discusses PDB protocol aggregation. GEGL operation headers and `E:COPYING.LESSER` establish LGPLv3-or-later for inspected library code, while `E:meson.build` labels the overall project `GPL3+`. Audit selected operations and dependencies rather than flattening the distribution into one permissive license.

**[I] Lesson / do not copy.** Borrow region-aware invalidation and bounded tile residency. Keep EveryGraph’s trusted in-process operators separate from externally executed extensions. Do not present process separation, operation registration, or an incremental work API as a security guarantee.

## 3. napari: scientific models, lazy data, and Python extensibility

**[S] Model/frontend separation.** `ViewerModel` owns dimension and layer models and inherits `EventedModel`; that class extends Pydantic and emits field-change events (`N:src/napari/components/viewer_model.py`, lines 147–216; `N:src/napari/utils/events/evented_model.py::EventedModel`). `QtViewer` is a Qt `QSplitter` holding the model and a `VispyCanvas`. This is a Python model layer with a Qt frontend, not evidence that Qt itself performs scientific image rendering. `N:pyproject.toml` explicitly declares NumPy, Dask, qtpy, VisPy, and npe2; this inspected branch offers PyQt6/PySide6 extras.

**[S] Rendering.** Image-layer adapters create image, tiled-image, and volume visuals. The image visual subclasses `vispy.scene.visuals.Image`, while scalar-field updates pass sliced data to `node.set_data` (`N:src/napari/_vispy/layers/image.py::ImageLayerNode`; `N:src/napari/_vispy/visuals/image.py`; `N:src/napari/_vispy/layers/scalar_field.py::_on_data_change`). GL-extension and texture-size checks are explicit. **[U]** This inspection does not establish a Metal/Vulkan-native napari renderer or exact driver compatibility.

**[S] Array contract and laziness.** `LayerDataProtocol` documents `dtype`, `shape`, indexing, `size`, and `ndim`; it intentionally describes capabilities rather than a closed list of accepted array classes. This is a NumPy-compatible, Array-API-inspired subset, not a guarantee of every NumPy protocol or universal zero-copy interoperability. The scalar-field slice request indexes first and then calls `np.asarray(data[tuple(slices)])`, explicitly materializing lazy data. Multiscale requests also handle thumbnail data. [Protocol](https://github.com/napari/napari/blob/753903212c83d8301cde57d3c1ceaf454d15a18b/src/napari/layers/_data_protocols.py#L42-L81); [materialization](https://github.com/napari/napari/blob/753903212c83d8301cde57d3c1ceaf454d15a18b/src/napari/layers/_scalar_field/_slice.py#L329-L347).

**[S] Responsiveness has qualifications.** `_LayerSlicer` creates a one-worker `ThreadPoolExecutor`; asynchronous execution depends on experimental settings and layer capability. It attempts cancellation of superseded pending tasks but retains synchronous paths (`N:src/napari/components/_layer_slicer.py`, lines 113–115, 164–255). Image `cache` documentation limits that option to Dask slices (`N:src/napari/layers/image/image.py`, lines 80–82). **[I]** Lazy inputs do not ensure bounded compute, instant cancellation, or absence of UI stalls; data-provider indexing and materialization still need budgets.

**[S] npe2 lifecycle.** Manifest discovery uses `napari.manifest` entry points; contributions can be indexed separately from activation (`P:src/npe2/manifest/schema.py`; `P:src/npe2/_plugin_manager.py::discover`, `register`). Command lookup can activate the owning plug-in, resolve its Python import path, and directly invoke the callable (`P:src/npe2/_command_registry.py::get`, `execute`). Activation calls `on_activate`; deactivation invokes `on_deactivate` and registered disposables. Deactivation does not itself disable the plug-in or remove indexed contributions. [Lifecycle](https://github.com/napari/npe2/blob/45215167b5c69047a3389b654cd0f8b063932164/src/npe2/_plugin_manager.py#L387-L453).

**[I] No sandbox assumption.** Deferred import improves discovery/startup behavior; it does not restrict imported Python or native extension code. Disposables are cooperative cleanup, not forced revocation of arbitrary side effects. **[S]** napari and npe2 have BSD-3-Clause manifests/license texts (`N:LICENSE`, `P:LICENSE`, respective `pyproject.toml` files); that does not relicense Qt bindings or installed plug-ins.

**[I] Lesson / do not copy.** Keep layer models testable without presentation, specify array capabilities, and make realization boundaries visible. Borrow declarative discovery, but put untrusted extensions behind a separately designed execution boundary rather than copying Python import-based trust.

## 4. Zed: Rust application boundaries and GPUI

**[S] Build/module architecture.** Zed is a Rust Cargo workspace with separate `editor`, `project`, `workspace`, `zed`, and GPUI/platform crates. The workspace defaults to `crates/zed`, uses Rust edition 2024, and disables default features on its GPUI dependency (`Z:Cargo.toml`, workspace/package/dependency sections). `gpui_platform::current_platform` selects concrete native platforms with target configuration; source-directory presence alone is not release support.

**[S] State and events.** GPUI’s `Entity<T>` is a typed retained handle; `WeakEntity<T>` does not retain the entity. Reads and updates pass through application contexts, with `update` receiving mutable entity state and `Context<T>` (`Z:crates/gpui/src/app/entity_map.rs::Entity`, `WeakEntity`, `update`). `Context::notify` signals state changes; `observe` and typed `subscribe` connect observers/events (`Z:crates/gpui/src/app/context.rs`, lines 61–105, 215–218). **[I]** This suggests explicit ownership and change delivery, not an automatically dependency-tracked spreadsheet engine.

**[S] Executors.** `BackgroundExecutor::spawn` accepts `Send` futures for background execution; `ForegroundExecutor::spawn` runs local futures on the main thread. A separate sendable foreground handle allows cross-thread submission (`Z:crates/gpui/src/executor.rs`, lines 18–48, 118–124, 376–382). **[I]** EveryGraph should similarly distinguish UI ownership from computation, while retaining an independent dependency scheduler and cancellation policy.

**[S] Actual graphics paths on inspected main.** macOS aliases its renderer to `gpui_apple::metal_renderer`; `MetalRenderer` owns Metal device/layer objects. Windows uses a DirectX renderer with `ID3D11Device`/`ID3D11DeviceContext`. Linux Wayland constructs `WgpuRenderer`; the wgpu crate enables Vulkan/GLES features, and native instance creation requests `VULKAN | GL`. These are separate paths—not “Metal everywhere,” and not evidence for WebGPU as the native macOS implementation. Sources: `Z:crates/gpui_macos/src/gpui_macos.rs`, line 17; `gpui_apple/src/metal_renderer.rs::MetalRenderer`; `gpui_windows/src/directx_renderer.rs`, lines 63–65; `gpui_linux/src/linux/wayland/window.rs`, line 587; [wgpu selection](https://github.com/zed-industries/zed/blob/422b53cff83699b36adcc401947e4f1eb338407a/crates/gpui_wgpu/src/wgpu_context.rs#L479-L487), with paths relative to `crates/` for the abbreviated locators.

**[D/S] macOS and Windows are shipped platforms.** The observed stable v1.26.2 release contains `Zed-aarch64.dmg`, `Zed-x86_64.dmg`, and both aarch64/x86_64 `.exe` installers. Its platform manifest selects macOS and Windows crates. Release installation docs support Windows 10 1903+ and Windows 11 22H2+, require 64-bit systems and DirectX 11, and list Intel/Apple macOS machines. These are official support statements plus artifact evidence, not locally tested compatibility. [Release requirements](https://github.com/zed-industries/zed/blob/c4273271092b0287f7d181f616bd5171e0a2f70c/docs/src/installation.md#L66-L122).

**[D/U] Branch/release matters.** At ZR, `docs/src/macos.md` says 10.15.7+, while installation documentation labels Catalina/Big Sur partially supported without collaboration screen sharing. At Z, the macOS page says 12.0+. Do not retroactively apply the main-branch minimum to v1.26.2 or promise an unreleased version’s final support policy. Release documentation still requires Vulkan 1.3 on Linux; main’s GL path is not proof of equivalent released support.

**[S] Licensing boundary.** `Z:crates/zed/Cargo.toml` specifies GPL-3.0-or-later and has `LICENSE-GPL`; `Z:crates/gpui/Cargo.toml` specifies Apache-2.0 and has `LICENSE-APACHE`. Inspected platform crates also declare Apache-2.0. **[I]** GPUI is a separately evaluable component, not permission to copy GPL application crates. Do not copy the workspace’s scale or assume its UI renderer provides EveryGraph’s plotting/export precision requirements.

## 5. llama.cpp: inference is another execution domain

**[S] Runtime API.** Root CMake declares C/C++; `L:src/CMakeLists.txt` builds `llama`, requests C++17, and links GGML. `L:include/llama.h` exposes a C interface with opaque model/context/sampler handles. Its lifecycle includes `llama_backend_init`, `llama_model_load_from_file`, `llama_init_from_model`, `llama_decode`, sampling, and explicit context/model destruction. Model parameters specify devices/GPU-layer placement; context parameters describe batching and execution. This is embeddable runtime machinery, not merely the command-line program or server. [API lifecycle](https://github.com/ggml-org/llama.cpp/blob/889f2ec96deacbc2d8a9a67dbe181eaa43a2fb3b/include/llama.h#L488-L563).

**[S] Backend-specific computation.** GGML’s backend interface supplies graph computation; device interfaces report operation and buffer compatibility (`L:ggml/src/ggml-backend-impl.h`, lines 130–155, 185–221). `L:src/llama-context.cpp::sched_new` constructs the scheduler and later submits `ggml_backend_sched_graph_compute_async`. [CPU execution](https://github.com/ggml-org/llama.cpp/blob/889f2ec96deacbc2d8a9a67dbe181eaa43a2fb3b/ggml/src/ggml-cpu/ggml-cpu.cpp#L170-L190) builds a threadpool-aware plan; [CUDA dispatch](https://github.com/ggml-org/llama.cpp/blob/889f2ec96deacbc2d8a9a67dbe181eaa43a2fb3b/ggml/src/ggml-cuda/ggml-cuda.cu#L2551-L2555) calls device-specific matrix operations; [Metal execution](https://github.com/ggml-org/llama.cpp/blob/889f2ec96deacbc2d8a9a67dbe181eaa43a2fb3b/ggml/src/ggml-metal/ggml-metal.cpp#L619-L622) calls `ggml_metal_graph_compute`; [Vulkan dispatch](https://github.com/ggml-org/llama.cpp/blob/889f2ec96deacbc2d8a9a67dbe181eaa43a2fb3b/ggml/src/ggml-vulkan/ggml-vulkan.cpp#L12850-L12855) selects its own matrix kernels. These are not one portable graphics shader pipeline.

**[S] Build boundaries and limits.** `L:ggml/src/CMakeLists.txt::ggml_add_backend` conditionally adds backends and can build loadable modules. Inspected backend CMake files enable CUDA, link Apple Metal frameworks, or require Vulkan/glslc and SPIR-V headers. **[U]** Kernel coverage, numerical equivalence, device-memory peaks, and throughput were not benchmarked. Importantly, `L:include/llama.h`, lines 402–405, describes the abort callback as currently CPU-only: universal GPU cancellation would be an unsupported promise.

**[S] Runtime license is not weight license.** `L:LICENSE` grants MIT terms for the software. Separately, `M:models/llama3_1/LICENSE` explicitly includes trained weights and imposes its own redistribution, attribution, acceptable-use, and commercial conditions. This is one concrete example, not a statement that all compatible models share Meta’s terms. [Weight agreement](https://github.com/meta-llama/llama-models/blob/0e0b8c519242d5833d8c11bffc1232b77ad7f301/models/llama3_1/LICENSE#L11-L33). **[I]** EveryGraph needs per-model provenance, license review, and artifact identification; a GGUF conversion must not be treated as a new permissive license.

**[I] Lesson / do not copy.** Place optional inference behind a narrow service/FFI contract with explicit context ownership, memory budgets, progress, and failure reporting. Do not couple document rendering to model inference, promise stable ABI merely because the API is C, or enable every backend because CMake exposes it.

## 6. EveryGraph planning conclusions and remaining unknowns

**[I] Recommended boundaries, derived from the sections above:**

1. Keep document/layer models independent of widgets and GPU resources, following napari’s separation and GPUI’s ownership discipline.
2. Specify computation dependencies and invalidation independently of render submission; borrow Blender’s dirty scheduling and GEGL’s spatial requirements without confusing their graph types.
3. Track semantic validity, CPU residency, GPU residency, and spilled data separately. Expose realization costs and avoid interpreting cache targets as process-wide limits.
4. Distinguish trusted native operators, user Python, and external tools. Treat discovery manifests, cleanup callbacks, and process boundaries as different mechanisms. Security requires explicit capabilities, IPC validation, and resource controls.
5. Evaluate a small graphics interface and a separate optional inference interface. Require target-hardware tests before promising backend parity; review application, framework, dependency, and model licenses separately.

**[U] Outstanding:** actual EveryGraph workload/latency and export requirements; backend performance and failure recovery on its target hardware; complete shader/kernel coverage; hard memory and cancellation behavior; adversarial extension containment; complete dependency/operation license inventories; and the final support floor of future Zed releases. This research establishes source architecture and observed release evidence, not production qualification, a security audit, or legal clearance.

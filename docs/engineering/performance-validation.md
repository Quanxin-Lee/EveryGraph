# Numerical and Performance Validation

Status: executable test plan, not measured application performance. Baseline date: 2026-10-30. The application does not yet exist. Compiler/planning checks do not establish CSV, numerical, graphics or memory performance.

## 1. Evidence tiers

1. Correctness reference: analytically known results, official certified datasets and independent trusted implementations.
2. Scalar/single-thread CPU reference: fixed semantics and precision; the first performance comparator.
3. Optimized implementation: must match declared numerical tolerances and improve end-to-end cost on both platforms.
4. Product workload: UI responsiveness, memory, save/export and concurrency with the same dataset/scene.

Use [NIST Statistical Reference Datasets](https://www.itl.nist.gov/div898/strd/) for statistical accuracy where applicable. Certified results test numerical accuracy, not runtime speed. SciPy/R or another library is a cross-check, not an oracle when both implementations share the same solver. Specify absolute/relative/ULP tolerances and expected failure behavior before evaluating results.

## 2. Reproducible fixture protocol

Store fixture generators, seeds, schema, byte size/row count, unit/null policy and content hashes. CSV sizes are **100,000,000 and 1,000,000,000 bytes** for the proposed tests; report actual generated bytes. Curves use exactly 1,000,000 and 10,000,000 points. Include numeric-only and mixed UTF-8/date/null/quoted CSV, wide tables, monotonic and non-monotonic x, gaps, outliers, sharp spikes and repeated timestamps. Scientific methods also include small edge cases, singular designs and ill-conditioned data.

Record OS/build, CPU/core count, RAM, storage, GPU/driver, display pixels/DPI, compiler/options, dependencies, power mode, thermal state and active background jobs. Establish at least one native Apple Silicon and one Windows x64 reference machine. Include a 16-GB-memory class if that remains a product target; do not generalize from the development Mac. Hardware IDs are currently unassigned.

Run release builds without a debugger. Separate cold-process and warm-process runs; OS page-cache state is separately recorded rather than falsely claiming it was cold. Warm up explicitly, run at least 10 independent trials (more for noisy measurements), randomize variant order and report median/p95 with dispersion. Long 1-GB tests may use fewer documented repetitions until automated resources exist. Do not compare instrumented and uninstrumented builds as equal performance runs.

Initial **design targets to validate**, not product promises: no deliberate blocking work on the UI thread; p95 command acknowledgement under 100 ms; p95 interactive pan/zoom frame under 33 ms after LOD is ready; bounded visible progress during longer preparation; cooperative cancellation normally acknowledged within 250 ms at an available checkpoint. Device initialization and noninterruptible foreign calls require explicit separate limits. CPU reference measurements may force justified revisions before a release commitment.

For throughput/startup/package/memory, do not invent absolute pass thresholds before reference hardware and a working application exist. At first baseline, set reviewed per-workload absolute budgets, plus an initial regression trigger of >10% median slowdown or >15% peak-memory increase outside observed noise. Correctness regressions fail regardless of speed. Keep first baseline artifacts versioned; the current status remains unmeasured.

## 4. Instrumentation

Use Instruments Time Profiler/Allocations/Metal tools on macOS; Visual Studio Profiler, Windows Performance Recorder/Analyzer and PIX where applicable on Windows. Use heap/copy counters at chunk builders/materialization/IPC boundaries, queue wait and execution timings at the scheduler, and upload/download counters at render/compute backends. FPS alone hides input latency and stall spikes. Include child processes and GPU memory in total footprint; report RSS/working-set/private bytes with platform-specific definitions rather than equating them.

ASan/UBSan check memory/undefined behavior; compatible TSan runs separately for races. MSVC ASan coverage differs from Clang; a passing Mac sanitizer run does not cover Windows adapters. Clang-Tidy and compiler warnings supplement runtime tests. Numerical tests cover empty/all-null input, huge/small magnitudes, overflow, units, sample spacing, weighted fits, degeneracy and nonconvergence. Randomized properties use fixed reproducing seeds.

## 5. Optimization decision sequence

Profile -> identify dominant end-to-end cost -> formulate one change -> benchmark identical semantics -> compare correctness/copies/memory/latency -> keep only measured benefit. Consider data layout, clipping, batching, bounded caches and lazy reads before SIMD/multithreading/GPU or language replacement. Include thread startup, IPC, conversion, synchronization and compilation/deployment cost. Parallel reductions may alter floating-point order; document tolerances and offer deterministic modes when required.

GPU compute is admitted per algorithm with CPU reference, supported-device coverage and fallback. Rust rewrites require evidence of safety/maintenance or measured runtime benefit; the language is not itself a performance test. A cache optimization must demonstrate correct invalidation and bounded residency. Screen downsampling never becomes the numerical input or silently degraded export.

## 6. Release acceptance and artifacts

Each benchmark result records fixture hash, repository revision, dependency lock, platform, metric distribution and profiler evidence. Save baseline/candidate comparison and explain exceptions. Numerical result records also include algorithm/version/options/seed and tolerance version. CI correctness runs can be frequent; stable-hardware performance runs are separate scheduled/release jobs to avoid treating noisy shared runners as a performance laboratory. Publication requires actual artifacts, not a successful compiler probe or anecdotal competitor claim.

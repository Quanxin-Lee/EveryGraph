## Scope and acceptance

Objective: close a trust-boundary hole in the accepted command kernel. `CommandGateway::CommandGateway(CommandRegistry, DocumentSnapshot, GatewayOptions)` at `modules/application/src/command_gateway.cpp:47-51` of the claimed tree moved `initial_state.objects` into `document_` without checking that each map key equals the stored `ObjectState::id`. A caller could therefore construct a gateway whose lookup key and the object's own identity disagree, which contradicts the AGENTS.md section 2 invariant that domain and data keep stable IDs and the section 5 rule that untrusted input is validated at system boundaries. The same constructor still occupies those lines now, with its parameter narrowed to a checked type — see the contract below.

The hole is latent, not live: `CommandTransaction::create_object` sets `state.id = id` and emplaces under the same `id`, so every mutation path maintains the invariant, and all three current builders key by the object's own id — `tests/application/command_kernel_tests.cpp:350-351` (`emplace(first.id, first)`), `tests/worker/worker_protocol_tests.cpp:287-289` (`snapshot.objects[kTarget] = state`) and `apps/desktop/src/fake_project.cpp:226-238`. What is missing is the guarantee at the boundary that a future loader, import or undo-from-disk path will feed this constructor, which is exactly the moment P2 persistence needs it.

Chosen contract (AC-1) and its reason: **reject, never re-key, and make the inconsistent state unrepresentable at the type the gateway reads.** `DocumentSnapshot` stays the plain caller-facing map; a new `ValidatedDocument` (`document.hpp:41-54`) holds the same map behind a private member with no accessor, and its only non-empty route is the static `ValidatedDocument::from(DocumentSnapshot)` (`document.cpp:12-28`), which returns `std::variant<ValidatedDocument, foundation::Error>`. `CommandGateway`'s constructor now takes `ValidatedDocument` instead of `DocumentSnapshot` (`command_gateway.hpp:39-40`, `command_gateway.cpp:47-51`), and `CommandGateway` keeps its original non-copyable, non-movable shape. A snapshot is refused when a map key differs from the `ObjectState::id` it stores, or when a key is the invalid `ObjectId` 0, with `foundation::ErrorCode::invalid_argument` and an English diagnostic naming both ids.

Re-keying was rejected for three reasons. It would silently repair a caller's mistake, which is the fallback AGENTS.md section 5 forbids ("add no arbitrary fallback that silently changes scientific semantics") — a loader that emitted two entries for one identity would keep emitting them and the corruption would reach persistence. It cannot be done losslessly: a map can already hold both `9 -> id 7` and, if the caller also wrote the object under its own id, a second entry for `id 7`, so no key choice preserves the caller's intent. And the invariant is about identity, which the caller owns: AGENTS.md section 2 makes stable domain IDs the domain's property, so the boundary's job is to refuse a foreign identity, not invent one.

Validating inside the gateway constructor was the shape this task first built, and review round 1 rejected it on evidence: a constructor cannot return an error, so that version needed a `CommandGateway::create` factory returning `std::variant<CommandGateway, foundation::Error>`, which in turn required a public move constructor because a variant alternative must be move-constructible. The reviewer reproduced the consequence — moving a live gateway leaves a listener subscribed before the move reading the moved-from document, and strands `OperationGuard`/`PublishingGuard`, which bind `bool&` to members, so the surviving object is permanently refused with `reentrant_mutation`. Making the checked value the gateway's parameter instead keeps the rejection on the type that owns the invariant and leaves the gateway immovable, which closes the hole without adding that hazard. No new `ErrorCode` enumerator was added: `invalid_argument` is what `document.cpp:57-59` already returns for an invalid object id, so the code stays stable and the specificity lives in the message. No C ABI is reached by exception or otherwise: a repository-wide search for `extern "C"` (excluding `out/`, `.git/` and `.venv/`) returns no match, so the gateway is reached only from C++ callers, and `from` throws nothing — it returns the error by value in the variant.

## Scope and acceptance

Objective: the macOS job requests a runner label that GitHub is removing. `.github/workflows/phase0.yml:14` says `runs-on: macos-14-xlarge`. GitHub announced that the macOS 14 Sonoma based runner images entered deprecation on 2026-07-06 and become fully unsupported for GitHub Actions and Azure DevOps on **2026-11-02** ([actions/runner-images#13518](https://github.com/actions/runner-images/issues/13518)), and the deprecation covers the `macos-14`, `macos-14-large` and `macos-14-xlarge` labels. The supported arm64 larger-runner labels in the [larger runners reference](https://docs.github.com/actions/reference/runners/larger-runners) are `macos-15-xlarge`, `macos-26-xlarge` and `macos-latest-xlarge`; the [runner-image lifecycle list](https://endoflife.date/github-actions-runner-images) puts macOS 14 arm64 support end at 2026-11-02.

Correction made during review on 2026-11-01, recorded rather than silently applied: Microsoft's [Azure Pipelines hosted-image deprecation schedule](https://learn.microsoft.com/en-us/azure/devops/pipelines/agents/hosted-deprecation-schedule) (document date 2026-10-31) states that the `macos-14` hosted image "will now be removed on November 23, 2026, instead of November 2, 2026" and extends the brownouts to 2026-11-20. That is the Azure DevOps side of this shared image family; the GitHub issue that governs `runs-on:` in a GitHub Actions workflow still carries the 2026-11-02 date and no update was found in it. The two dates are recorded as a live source conflict, GitHub's 2026-11-02 is the one this repository's workflow is exposed to, and either way the label is deprecated and scheduled for removal — the change this task makes does not depend on which date proves correct. The scaffold's "the deprecation covers `macos-14`, `macos-14-large` and `macos-14-xlarge`" sentence is unaffected.

The workflow triggers on `push`, `pull_request` and `workflow_dispatch` (`phase0.yml:3-7`), and this repository has no authorized push path in the current round, so no run fails until a push or dispatch happens. `macos-26-xlarge` is chosen because it is the only **explicitly versioned** supported arm64 xlarge label whose default toolchain prints AppleClang 21.0.0 — the compiler version every recorded local run in the development guide uses — so the versions the job prints at `phase0.yml:28-36` move *toward* the qualified baseline instead of to a compiler two majors older, which is what the retiring `macos-14-xlarge` printed (15.0.0) and what `macos-15-xlarge` would print (17.0.0). `macos-latest-xlarge` prints 21.0.0 too but is rejected on that ground alone: it is an alias that floats with GitHub's default, so the label would silently change toolchains under the job later, and this repository pins what it depends on. The job's `test "$(uname -m)" = arm64` assertion keeps its original meaning under any of these, since all are arm64.

The stronger reason to reject `macos-15-xlarge` is lifecycle, not compiler age. GitHub's published image support policy is at most two GA images plus one beta at a time, and macOS 15 is now the oldest supported GA macOS family — the same position macOS 14 held when its deprecation notice opened — so choosing it buys no runway and recreates this exact one-line churn in the next round (**inference from the published policy**: no GitHub notice announcing a macOS 15 retirement date was found on 2026-11-01, and the search returned only secondary coverage, so macOS 15's own end date is recorded as **unknown**, not as a fact).

What changes with the image, stated plainly: the runner OS moves from the macOS 14 family — which matched the macOS 14.4+ minimum qualification target — to macOS 26, so the job no longer exercises a near-minimum host OS; `sw_vers` prints 26.x, `xcode-select -p` prints an Xcode 26.6 path, `xcrun clang++ --version` prints AppleClang 21.0.0 rather than 15.0.0, and `xcrun --show-sdk-version` prints a 26.x SDK rather than 14.x. The deployment target stays 14.4 because the presets set it (`CMakePresets.json:33`), not the image. No run has been performed, so these four lines are the image inventory's stated contents, not observed CI output. The match is nominal and confers no equivalence: nothing in the job reads the printed versions, the 21.0.0 on a macOS 26.6.2 host with a 26.x SDK is a different compile environment from the recorded local macOS 27.0.1 / build 26A434 / SDK 27.0 one, and the accepted substitution ban in Out of scope below still holds.

Out of scope: running or dispatching the workflow, reading Actions run history, changing the pinned `cmake==3.31.6` and `ninja==1.11.1.4` installs, re-baselining the local AppleClang toolchain, adding a matrix over macOS images, and any claim that a macOS 15 or 26 runner result substitutes for the locally qualified macOS 14.4+ Apple Silicon evidence.
